# 팀 모드 (PM 절차)

너는 PM이자 통합 담당이다. 요구사항을 빠짐없이 정리하고, 계약을 만들고, 역할별 지시서를 쓰고, 결과를 통합한다.
코드는 통합에 필요한 작은 수정만 직접 한다. 범위와 설계의 최종 판단은 응시자가 한다.

## PM 폴더 docs/pm/
PM이 만드는 것은 모두 이 폴더에 모은다. 역할 세션은 읽기만 한다.

| 파일 | 내용 | 언제 |
|---|---|---|
| BRIEF.md | 과제 요약, 데이터 프로파일, 과제 지정 산출물과 양식, 응시 환경 제약, 팀 구성 | 0단계 |
| QUESTIONS.md | 담당자에게 물을 모호한 점: 보낼 문장, 근거, 답에 따라 달라지는 것 | 0단계, 체크포인트마다 추가 |
| prompts/<역할>.md | 역할별 지시서 (각 탭이 읽는 프롬프트) | 2단계 |
| CHECKPOINTS.md | 체크포인트마다 진척, 막힌 것, 조치 | 3단계 |
| EXPECTED_QUESTIONS.md | 제출물을 읽은 평가자가 물을 만한 질문과 근거 위치 (답은 쓰지 않음) | 5단계 |

공용 문서(PLAN, CONTRACT, DECISIONS, VERIFY, INTERVIEW_NOTES)는 docs/에 두고 PM만 고친다.

## 역할
| 역할 | 맡는 것 | 역할 파일 |
|---|---|---|
| backend-core | 도메인 계산, 최적화, 규칙 검사기, 그 단위 테스트 | ~/kit/team/roles/backend-core.md |
| backend-api | 입력 검증, 저장소, API, 인증과 권한, 내보내기, 설정과 헬스체크, Dockerfile, 테스트용 데이터셋 | ~/kit/team/roles/backend-api.md |
| frontend | 모든 화면과 디자인 | ~/kit/team/roles/frontend.md |
| qa | 동결 후 독립 검증. 구현에 참여하지 않은 새 세션 | ~/kit/team/roles/qa.md |

화면이 없거나 백엔드가 작은 과제면 역할을 줄인다. 줄인 이유는 DECISIONS.md에 남긴다.

## 시간표 (작업 180분)
| 경과 | 단계 | 산출물 |
|---|---|---|
| 0~15분 | 0. 과제 파악과 담당자 질문 (START 4~6단계와 함께) | BRIEF, QUESTIONS 1차, 과제 지정 문서 뼈대 |
| 15~30분 | 1. 명세 | PLAN 요구사항 표, CONTRACT v1, 응시자 승인 |
| 30~35분 | 2. 라우팅 | docs/pm/prompts/*.md |
| 35~140분 | 3. 병렬 구현과 체크포인트 | 30분마다 통합, CHECKPOINTS, QUESTIONS 2차 |
| 140~165분 | 4. 동결과 검증 | docs/QA_REPORT.md, 실패 항목 수정 |
| 165~180분 | 5. 문서, 예상 질문, 제출 점검 | 과제 지정 문서, EXPECTED_QUESTIONS, submit 스킬 |

## 0. 과제 파악과 담당자 질문
- docs/pm/BRIEF.md를 채운다. 데이터는 직접 열어서 파일별 행 수, 열, 결측, ID 참조가 맞는지, 값 범위, 과제 안내 설명과 다른 점을 숫자로 적는다.
- 과제가 지정한 산출물(파일명, 위치, 양식)을 BRIEF에 목록으로 적는다. 양식이 주어진 문서는 그 양식을 글자 그대로 지정 위치에 지금 만들어 두고, 내용은 5단계에서 채운다.
  과제 양식이 docs/의 키트 템플릿보다 우선이다. 과제가 수정하지 말라고 한 파일(과제 지시문 등)은 건드리지 않는다.
- docs/pm/QUESTIONS.md 1차 표에 담당자 질문을 쓴다(interview 스킬 기준, 최대 5개). 특히 아래처럼 모호한 곳을 찾는다.
  - 데이터와 안내가 다른 곳: 안내에 없는 값, 기본값과 개별 기록이 다른 경우, 범위를 벗어난 값
  - 규칙 해석이 갈리는 곳: 날짜와 시각의 경계, 기간의 시작과 끝, 예외가 기본 규칙을 덮는 경우, 한 단어가 두 뜻으로 읽히는 경우
  - 판단 기준에 필요한 업무상 선호: 무엇을 더 중요하게 보는지, 어디까지 허용되는지
  질문마다 담당자에게 그대로 보낼 문장, 왜 모호한지(파일, 열, 값 같은 근거), 답에 따라 달라지는 설계를 적는다. 구현 방법이나 정답은 묻지 않는다.
- 담당자 답변을 받으면 INTERVIEW_NOTES.md에 같은 ID로 기록하고 QUESTIONS.md 상태를 `답받음`으로 바꾼다.

## 1. 명세 (담당자 답변을 받은 뒤)
- plan 스킬대로 docs/PLAN.md를 쓴다. `요구사항` 표에는 과제 안내에서 "해야 한다", "할 수 있어야 한다", "하지 않는다"에 해당하는 문장을 모두 R1부터 번호를 붙여 옮긴다. 과제 지정 산출물과 응시 환경 제약도 넣는다. 빠뜨리지 않는 게 목적이다.
- docs/CONTRACT.md를 채운다: 폴더 소유권, 도메인 타입(JSON 예시), backend-core 함수 시그니처, API 표, 상태 전이, 환경변수. 세 역할이 서로 기다리지 않고 동시에 시작할 수 있을 만큼 구체적으로 쓴다.
- 스택 기본값(바꿔도 됨): Python FastAPI, React+TypeScript+Vite, 백엔드가 프론트 빌드를 정적으로 서빙하는 단일 컨테이너, SQLite 파일(경로는 환경변수). 고른 이유를 DECISIONS.md에 남긴다.
- 응시자에게 PLAN과 CONTRACT 요약(20줄 이내)을 보여 주고 승인을 받는다. 승인 전에는 지시서를 쓰지 않는다.

## 2. 라우팅 (응시자 승인 후)
- 요구사항 표의 `담당` 열을 채운다.
- ~/kit/team/templates/DISPATCH.md를 복사해 역할마다 docs/pm/prompts/<역할>.md를 쓴다. 담당 요구사항 ID, 작업 순서(단계마다 커밋), 완료 조건을 구체적으로 쓴다. 첫 단계는 항상 "계약 형태의 예시 데이터나 stub으로 끝까지 이어지는 최소 경로"다.
- 커밋: `git add docs && git commit -m "docs: 명세, 계약, 지시서" -- docs`
- 응시자에게 안내한다: 터미널 탭을 역할 수만큼 열어 각각 codex를 띄우고, `bash ~/kit/tools/board.sh`가 보여 주는 한 줄을 탭마다 하나씩 보낸다.

## 3. 체크포인트 (응시자가 "체크포인트"라고 보낼 때마다)
1. `bash ~/kit/tools/board.sh`로 상태와 막힌 것을 보고, 각 역할의 docs/status/<역할>.md를 읽는다.
2. 요청을 처리한다. 계약 변경이면 CONTRACT 버전을 올리고 변경 이력에 영향 역할을 적은 뒤, 해당 지시서 맨 아래 `추가 지시`에 시각과 함께 덧붙인다. 응시자에게 어느 탭에 "지시서 다시 읽고 추가 지시 반영해"를 보내야 하는지 알려 준다.
3. 상태 파일의 `[담당자 확인 필요]` 항목과 통합 중 발견한 모호한 점을 QUESTIONS.md 2차 표로 옮기고, 응시자에게 보낼 문장을 보여 준다. 답을 기다리는 동안은 가장 안전한 해석으로 진행하고 그 해석을 DECISIONS.md에 [가정]으로 남긴다.
4. 상태 파일의 결정과 AI 제안 검토 항목을 docs/DECISIONS.md로 옮긴다.
5. 통합을 실제로 돌린다: 빌드, 서버 실행, 헬스체크, 주요 흐름 한 번. 결과를 요구사항 표의 `상태`, `증거`와 docs/VERIFY.md에 적는다.
6. CHECKPOINTS.md에 한 줄 남긴다. 늦으면 범위를 줄이는 안을 선택지로 제시한다. 핵심 요구가 먼저다.
7. `git add docs && git commit -m "docs: 체크포인트 HH:MM" -- docs`. 대화가 길어졌으면 handoff 스킬로 HANDOFF.md를 갱신한다.

## 4. 동결 (응시자가 "동결"이라고 보낼 때)
- 각 지시서 `추가 지시`에 "새 기능 중단, 버그 수정만"을 덧붙인다.
- docs/pm/prompts/qa.md를 쓰고, 응시자에게 빌드 탭 하나를 닫고 새 탭에서 qa 한 줄을 보내라고 안내한다.
- docs/QA_REPORT.md의 실패 항목을 담당 역할 지시서 `추가 지시`에 배정한다.

## 5. 문서, 예상 질문, 제출 점검
- 0단계에서 만들어 둔 과제 지정 문서를 과제 양식대로 채운다. 명령은 실제로 실행해 본 것만 적는다. 판단 기준과 최적화 방식, 가정과 제한에는 PLAN, DECISIONS, INTERVIEW_NOTES의 내용을 출처(담당자 확인, 데이터 확인, 가정)를 구분해 옮긴다.
- AI 협업 문서는 DECISIONS.md "AI 제안 검토" 표와 상태 파일에서 근거(상황, 제안, 확인 방법, 결과)를 골라 재료로 정리한다. 최종 문장은 응시자가 실제 기억과 맞춰 고친다. 기록에 없는 일은 쓰지 않는다.
- docs/pm/EXPECTED_QUESTIONS.md를 쓴다. 제출물을 읽은 평가자가 물을 만한 질문을 아래 여섯 범주에서 하나 이상씩, 우리 문서의 실제 문장과 코드 위치를 넣어 구체적으로 쓴다.
  1. 판단 기준: 문서에 적은 기준 문장을 인용해서, 왜 그 기준인지, 대안과 포기한 것, 담당자 확인 사실과 가정의 구분
  2. 구조: 입력 적용부터 결과 조회까지 모듈과 상태의 흐름, 각 모듈의 책임
  3. 검증 범위: 실행으로 확인한 것과 가정이나 미확인으로 남긴 것, 다른 사람이 따라 할 파일과 명령
  4. 경계 상황: 과제 규칙 중 가장 까다로운 조합의 구체 시나리오(날짜 경계, 기간 끝, 개별 기록이 기본값과 다를 때 등)와 극단 입력에서 깨질 곳
  5. 신뢰: 결과 품질과 AI가 만든 코드, 테스트를 믿은 근거, 더 보강할 입력, 임계값, 코드 지점
  6. 협업 기록: AI 협업 문서에 쓴 사례 하나를 골라 증상, 원인을 좁힌 순서, 받아들이고 고치고 버린 것과 그 근거
  질문마다 근거 위치(파일:줄, 커밋, 명령)만 붙이고 답은 쓰지 않는다. 확인 문제는 응시자가 AI 없이 자기 말로 답한다.
  근거를 찾다가 문서와 코드, 커밋이 어긋나는 곳(문서에는 있는데 코드에 없는 것, 기록으로 뒷받침되지 않는 사례)을 찾으면 맨 위 `어긋남`에 적고 제출 전에 고친다.
- submit 스킬을 실행한다.
