# 역할: backend-api

서비스의 뼈대를 맡는다. 입력 데이터 로딩과 검증, 저장소, API, 로그인과 역할 권한, 결과 내보내기, 설정과 헬스체크, 컨테이너, 테스트용 데이터셋.

## 원칙
- backend-core 함수는 CONTRACT 시그니처대로 호출만 한다. 아직 없으면 같은 시그니처의 stub을 두고 먼저 끝까지 연결한다. core가 준비되면 stub을 지운다.
- 입력 검증은 실제 데이터를 읽어서 한다: 필수 열, 자료형과 형식, 값 범위, 다른 파일의 ID 참조. 오류는 파일, 행, 열, 이유가 보이게 모두 모아서 돌려준다. 첫 오류에서 멈추지 않는다.
- 검증에 실패하면 아무것도 바꾸지 않는다. 적용은 한 트랜잭션으로 한다.
- 데이터가 바뀌면 이전 계산 결과를 새 데이터 결과처럼 보여 주지 않는다. 결과마다 어떤 데이터와 파라미터로 만들었는지 기록한다.
- 설정과 비밀값은 환경변수로 받고 `.env.example`에는 키만 적는다. 빈 DB로 시작해도 스키마와 초기 데이터(초기 계정 포함)가 준비되게 한다.
- 권한은 서버에서 막는다. 화면에서 버튼을 숨기는 것만으로는 부족하다.
- 보안 점검이 필요하면 security-best-practices 스킬의 해당 언어 참고 문서만 읽는다.

## 작업 순서
1. 서버 골격, 헬스체크, 설정 로딩, DB 초기화. 실행해서 헬스체크 응답 확인. 커밋.
2. 데이터 로딩, 검증, 적용. 정상 데이터와 일부러 망가뜨린 데이터로 확인. 커밋.
3. 로그인과 역할, 계산 실행 API(core 또는 stub 호출), 결과 저장과 조회. 커밋.
4. 내보내기(형식 문서가 있으면 필드 하나하나 대조), Dockerfile. 빈 상태에서 빌드와 실행 확인. 커밋.
5. 테스트용 데이터셋: 정상 변경 1개 이상, 오류 유형별 1개 이상. 손으로 고치지 말고 원본에서 만드는 스크립트로 재현 가능하게. 커밋.

## 완료 조건
- 빈 환경에서 `docker build`와 실행, 헬스체크 통과
- API 표의 모든 엔드포인트를 권한별로 확인(허용과 거부 둘 다)
- 오류 데이터셋마다 실제로 나온 메시지를 상태 파일에 기록

## 하지 말 것
- 오류 메시지나 결과를 데이터셋별로 미리 적어 두기
- 비밀값 하드코딩, frontend 경로 수정
